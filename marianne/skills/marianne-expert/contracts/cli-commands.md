# Marianne CLI Commands (`mzt`)

This contract catalogs all CLI commands exposed by the `mzt` tool (built with Typer), grouped by functional panels.

---

## 1. Getting Started
Commands for initializing, composing, and compiling scores.

*   **`init`**
    *   *Purpose:* Initialize a fresh Marianne project directory with standard folder structures, specs, and config files.
*   **`compose`**
    *   *Purpose:* Interactive score generation wizard translating intent into declarative score files.
*   **`compile`**
    *   *Purpose:* Compiles modular agent profiles and spec files into unified executable score YAML.

---

## 2. Score Runs
Commands for managing execution runs.

*   **`run <score.yaml>`**
    *   *Purpose:* Submit a score YAML to the conductor for execution.
    *   *Options:* `--fresh` to ignore checkpoints and start fresh.
*   **`resume <job_id>`**
    *   *Purpose:* Continue a paused, stopped, or failed job run from its last checkpoint.
*   **`pause <job_id>`**
    *   *Purpose:* Request the conductor to pause execution of a running job after current sheets finish.
*   **`resolve <job_id>`**
    *   *Purpose:* Force-resolve a FERMATA (paused for developer decision) sheet, specifying action (e.g., retry or fail).
*   **`modify <job_id>`**
    *   *Purpose:* Modify execution variables and config on a paused job before resuming.
*   **`cancel <job_id>`**
    *   *Purpose:* Terminate a job run, stopping all in-flight sheet tasks.
*   **`validate <score.yaml>`**
    *   *Purpose:* Parse and validate score structure, dependencies, and syntax. Doesn't require daemon.
*   **`recover <job_id>`**
    *   *Purpose:* Recover a job stuck in an inconsistent status after daemon crash.

---

## 3. Monitoring
Commands for tracking conductor activity.

*   **`status [job_id]`**
    *   *Purpose:* Print a detailed execution progress report of a job.
*   **`watch <job_id>`**
    *   *Purpose:* Live stream output blocks and validation results as sheets execute.
*   **`list`**
    *   *Purpose:* List execution history and status of all jobs registered with the conductor.
*   **`top`**
    *   *Purpose:* Launch an interactive terminal UI dashboard (built with Textual).
*   **`clear`**
    *   *Purpose:* Remove completed or failed job metadata from the conductor database.

---

## 4. Diagnostics
Commands for debugging and log inspection.

*   **`logs`**
    *   *Purpose:* Retrieve or tail logs generated by the conductor daemon.
*   **`errors [job_id]`**
    *   *Purpose:* Show error history and backtrace context for failed sheet runs.
*   **`diagnose <job_id>`**
    *   *Purpose:* Scan logs, state databases, and workspace files to pinpoint execution failures.
*   **`history [job_id]`**
    *   *Purpose:* Display detailed execution timeline including timestamps and durations.
*   **`doctor`**
    *   *Purpose:* Run readiness checks on the execution environment (PATH, CLI agents, credentials).

---

## 5. Services
Commands for hosting APIs and dashboards.

*   **`dashboard`**
    *   *Purpose:* Start the local web-based monitoring dashboard interface.
*   **`mcp`**
    *   *Purpose:* Start Marianne conductor as a Model Context Protocol server.

---

## 6. Conductor
Commands for daemon lifecycle management.

*   **`start`**
    *   *Purpose:* Start the conductor daemon in the background (double-fork).
*   **`stop`**
    *   *Purpose:* Stop the running conductor daemon cleanly.
*   **`restart`**
    *   *Purpose:* Cleanly stop and restart the conductor daemon.
*   **`conductor-status`**
    *   *Purpose:* Query the daemon status (socket connections, active PID).
*   **`clear-rate-limits`**
    *   *Purpose:* Force-clear all active rate-limiting cooldown timers.

---

## 7. Configuration and Profiles
Commands exposed as sub-apps in Typer.

*   **`config show|check`**
    *   *Purpose:* View, verify, or update conductor daemon configurations.
*   **`instruments list|check`**
    *   *Purpose:* Discovery sub-app. `list` lists configured instruments; `check` performs a path/connectivity verify on one profile.

---

## 8. Learning
Commands for examining the telemetry database and self-healing.

*   **`patterns-list`**
    *   *Purpose:* List optimization and error-remediation patterns registered by learning.
*   **`patterns-why <pattern_id>`**
    *   *Purpose:* Trace the history and efficacy of a specific pattern.
*   **`patterns-entropy`**
    *   *Purpose:* Report Shannon entropy and pattern distribution variety.
*   **`patterns-budget`**
    *   *Purpose:* Inspect or adjust exploration and self-healing budgets.
*   **`learning-stats`**
    *   *Purpose:* Show size and execution record stats of global telemetry database.
*   **`learning-insights`**
    *   *Purpose:* Summarize general rules and adjustments made by self-healing.
*   **`learning-drift`**
    *   *Purpose:* Analyze concept drift across execution contexts.
*   **`learning-epistemic-drift`**
    *   *Purpose:* Map epistemic drift and model uncertainty metrics.
*   **`learning-activity`**
    *   *Purpose:* List chronological learning entries.
*   **`learning-export`**
    *   *Purpose:* Dump learning data into transportable formats.
*   **`learning-record-evolution`**
    *   *Purpose:* Execute a database schema self-evolution score.
*   **`entropy-status`**
    *   *Purpose:* Report database diversity alerts.
