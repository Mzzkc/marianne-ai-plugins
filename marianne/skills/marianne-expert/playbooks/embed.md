# Embedding Marianne Behind an App

## Problem
App authors are likely to wrap Marianne by shelling out to `mzt run`, exposing score paths in the UI, or promising runtime capabilities that are only schema, docs, or operator intent. The mistake is a boundary error: the product surface should speak domain verbs, while the adapter should preserve Marianne's runtime contract, validation contract, status model, and security limits. The governing evidence is that dispatch is a runtime scheduler with implemented concurrency, rate-limit, and stagger gates [C004, C005, C006, C007, C008]; validation commands can execute privileged shell work and therefore assume trusted score authors [C015]; status has bounded job and sheet enums that an app can map without parsing prose [C041, C042]; and several attractive "platform" surfaces are partial, spec-only, or runtime-unwired rather than deployable app capabilities [C026, C027, C028, C029, C030, C031, C032, C033].

## Mechanism
Embed Marianne through a thin backend adapter that validates the score or durable app-owned score path, checks the conductor, submits hidden jobs, polls status, and writes an app-local audit record for submit, cancel, resume, and settings changes. The user-facing service should expose product verbs such as "generate candidates" or "verify outputs"; it should not require users to understand score YAML, workspaces, sockets, or raw `mzt` commands. Runtime scheduling is handled by `dispatch_ready()`, which is a stateless free function [C004]. Code and tests show that `dispatch_ready()` enforces the global concurrency ceiling; one configuration reference denying enforcement is stale, so treat enforcement as runtime truth and record the docs-only denial as stale [C005]. The same dispatch path supports per-instrument or per-model concurrency [C006], checks rate-limited instruments [C007], and applies a monotonic-clock stagger gate [C008].

The adapter contract should be harness-neutral: accept a score reference or persisted generated score, `runtime_variables`, workspace intent, dry-run/fresh/self-healing flags if the product exposes them, and return a typed envelope such as `accepted`, `pending`, `running`, `completed`, `failed`, `paused`, `paused_at_chain`, or `cancelled` using the seven implemented job states [C041]. For detail panes, map sheet state to the eleven implemented scheduling states instead of scraping log prose [C042]. If the app allows relative workspace paths, label it security-sensitive before use: score YAML workspaces resolve relative to the score file's parent directory, preserve absolute paths, and are not a confinement boundary [C038]. If the app persists job state, do not claim daemon-wide JSON state: `JobConfig` supports `json` or `sqlite`, while the daemon config remains fixed to sqlite [C037].

Capability detection must be at capability level, not feature-name level. A2A has in-memory runtime structures that are not checkpointed, so an app can expose same-run delegation only with a restart-loss caveat [C026]. A2A completion and failure events are serialized observer surfaces, but execution does not fire or handle them [C027, C028]. The docs say `CronTick` submits and reschedules jobs, but source/tests show the event loop only logs an unimplemented warning. Treat the warning-only handler as runtime truth and record scheduling prose as stale or contradicted [C029]. The docs say `ConfigReloaded` rebuilds pending sheets, but source/tests show the handler only logs an unimplemented warning. Treat the warning-only handler as runtime truth and record hot reload prose as stale or contradicted [C030]. The docs say grounding hooks validate outputs, but source/tests show grounding config validates structurally and no runtime path invokes hooks. Treat runtime-unwired grounding as truth and record active validation prose as stale or contradicted [C031].

Operator lifecycle controls should be conservative. Conductor start writes a PID file protected by `fcntl.flock`, so duplicate-start detection is a process-level guard the app can respect [C034]. Do not stop or restart the conductor from an app while jobs are active; the event inbox is intentionally unbounded and is an implemented security risk for OOM/DoS if an embedding layer floods it [C009]. Orphan cleanup is not an operator toggle. Orphan reaping is a known broken safety no-op due to WSL2 shutdown risk [C032]. The docs or claim say a module-level orphan-reaping disabled flag exists, but source/tests show no such flag; the methods are hardcoded no-ops. Treat the no-op method bodies as runtime truth and record the flag claim as false [C033].

## Evidence
Use dispatch claims for hidden submission semantics: `dispatch_ready()` is the actual scheduling boundary [C004], global concurrency is implemented despite stale docs [C005], per-instrument/model limits are implemented [C006], rate-limit checks are implemented [C007], and stagger gating is implemented with monotonic time [C008]. These claims support an app adapter that submits work and observes scheduler outcomes rather than trying to perform scheduling in the UI.

Use validation and path claims for trust boundaries. `command_succeeds` is part of the retryable validation surface and is security-sensitive because it is privileged bash for trusted score authors [C015]. Validation commands spawn in new sessions [C016], include an implemented but directly untested daemon-PGID refusal path [C017], and terminate process groups with SIGTERM, a two-second grace period, then SIGKILL [C018]. Relative workspace resolution is security-sensitive because score-relative paths can resolve outside the user's assumed app directory [C038].

Use status and capability claims for app-facing contracts. Job and sheet states are enumerable [C041, C042], A2A state is partially implemented and memory-only [C026], A2A completion/failure events are spec-only observer serialization rather than executed lifecycle events [C027, C028], cron and config reload are spec-only warning handlers [C029, C030], grounding is config-only runtime-unwired [C031], and orphan reaping is a known broken safety no-op without a module-level flag [C032, C033]. Output capture is 51,200 bytes / 50 KiB; a test docstring saying 10KB is stale only if the stale comment itself matters [C048].

## Trap
Tempting sentence: "The app can expose Marianne's scheduler, hot reload, grounding, A2A completion events, and orphan cleanup as backend capabilities."

Correction: "Expose only implemented capabilities by default; label partial, spec-only, runtime-unwired, false, and safety-noop surfaces before they reach product UI." A2A state is memory-only [C026], A2A completion/failure execution is spec-only [C027, C028], cron and config reload only log warnings [C029, C030], grounding does not run hooks [C031], and orphan reaping is a hardcoded no-op with no flag [C032, C033].

Concrete consequence: a user may believe the app scheduled work, reloaded config, validated integrity, persisted delegation, or cleaned leaked processes when Marianne did not execute any of those actions.

## Verify
1. Before publishing the embedding guide or wiring the adapter, scan for runtime verbs such as "runs", "validates", "schedules", "reloads", "persists", "reaps", and "native"; attach a claim ID to each factual statement or delete it.
2. Confirm the adapter hides raw score mechanics behind product verbs, but still accepts the operator fields it chooses to expose as explicit contract inputs: score path or durable generated score path, runtime variables, workspace, dry run, fresh, self-healing, and resume/cancel intent.
3. Confirm every submit path validates score/config content before dispatch and records an audit event. If `command_succeeds` is possible, label it trusted-author privileged bash before any recipe tells a user to enable it [C015].
4. Confirm job polling maps only the seven `JobStatus` states [C041] and detail views map only the eleven `SheetStatus` states [C042]. Do not parse human log text for state.
5. Confirm capability detection marks A2A as memory-only [C026], A2A completion/failure execution as spec-only observer serialization [C027, C028], cron and config reload as spec-only warning handlers [C029, C030], grounding as config-only runtime-unwired [C031], and orphan reaping as known broken safety no-op with no module-level flag [C032, C033].
6. Confirm source precedence is explicit for contradictions: source/tests win over stale docs for global concurrency [C005], cron [C029], config reload [C030], grounding [C031], orphan cleanup flag claims [C033], and the 50 KiB output capture limit when a stale 10KB test comment appears [C048].
