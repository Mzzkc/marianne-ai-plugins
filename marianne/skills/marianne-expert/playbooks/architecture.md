# Architecture Playbook

## Problem

Maintainers are likely to misread Marianne as a single conductor loop that owns every concern: scheduling, prompt rendering, tool access, backend execution, persistent state, plugins, A2A, and future automation. The architecture boundary is sharper than that. The conductor process owns daemon lifetime and single-instance startup; the baton owns event/state progression; `dispatch_ready()` is a stateless scheduling function called after baton events; musicians execute sheet attempts through instrument backends; adapters expose protocol-specific surfaces such as A2A without making those surfaces restart-persistent. [C004, C009, C026, C034] The likely wrong action is to describe planned or serialized surfaces as active runtime capabilities, especially cron scheduling, config reload, grounding hooks, and A2A completion/failure propagation. [C027, C028, C029, C030, C031] The governing boundary is source precedence: executable code and tests win over design prose, stale comments, and attractive architecture names.

## Mechanism

The conductor is the daemon boundary. It starts as a single writer guarded by PID-file advisory locking, so two daemon instances do not concurrently mutate the same state. [C034] The baton is the runtime coordination boundary. `BatonCore` owns an event inbox, but that inbox is an unbounded `asyncio.Queue`; this is implemented with an OOM/DoS risk, not backpressure. [C009] The scheduling decision is deliberately outside `BatonCore`: `dispatch_ready()` is a free function that receives the baton, evaluates ready sheets, and dispatches only when concurrency, rate-limit, and stagger gates allow it. [C004] It enforces global concurrency, although one configuration document is stale where it says global concurrency is not enforced; source/tests show the global ceiling exists, so treat the source behavior as runtime truth and the conflicting prose as stale docs. [C005] It also supports per-instrument and per-`instrument:model` concurrency, skips rate-limited instruments, and uses a monotonic-clock stagger gate. [C006, C007, C008]

The musician boundary is attempt execution. Sheet prompt templates are stored raw and rendered at dispatch time, so cross-sheet context can exist before rendering; that is baton-side runtime behavior, not compile-time text expansion. [C002, C003] Instrument execution then flows through resolved profiles and shared execution contracts. The pinned evidence records an intermediate Atlas topology with profile-driven Claude CLI, two provider-specific clients, and generic `recursive_light` dispatch [C020, C021, C023, C024, C025]. That inventory is historical. Inspect current source, profile YAML, dispatch, and tests before describing which executors or names exist now. Provider-specific behavior belongs in reusable schema codecs rather than permanent provider-class exceptions.

The plugin system should be described in two layers. The implemented capability layer is ECS techniques: each technique has kind `skill`, `mcp`, or `protocol`; runtime technique resolution determines which techniques are active during sheet phases; the router classifies A2A requests and tool-like output but does not execute MCP calls itself. [C010, C011, C012, C013] The compact interface layer generates Python stubs for MCP tools so sandboxed or isolated agent code can import compact interfaces without requiring Marianne inside the sandbox. [C014] This is plugin/tool access plumbing, not proof that every protocol surface is durable or fully executed.

State ownership is split. Job and sheet lifecycle states are persisted through the configured state backend, with job statuses and sheet statuses defined in checkpoint enums and SQLite schema version 4 for the SQLite backend. [C041, C042, C044] Job configuration supports `state_backend` values `json` and `sqlite`, but daemon-wide state backend configuration remains narrower; do not generalize job-level support into a daemon-wide storage abstraction. [C037] A2A runtime state is different: `_a2a_registry` and `_a2a_inboxes` live in memory and are not checkpointed, so restart persistence is only a future schema extension. [C026] Relative workspace paths resolve against the score file's parent directory without confinement, so score path handling is implemented but security-sensitive for untrusted scores. [C038]

Several surfaces are spec-only or runtime-unwired. The docs say `CronTick` submits jobs and schedules the next tick, but source/tests show the baton event loop only logs an unimplemented warning. Treat the warning-only no-op as runtime truth and the scheduling prose as stale or contradicted. [C029] The docs say `ConfigReloaded` rebuilds pending sheets, but source/tests show the handler only logs an unimplemented warning. Treat the warning-only no-op as runtime truth and record the hot-reload prose as stale or contradicted. [C030] Grounding configuration validates structurally, but runtime does not invoke grounding hooks; docs describing active output validation from grounding are stale. [C031] A2ATaskCompleted and A2ATaskFailed are event classes and observer surfaces, but execution does not fire or handle them. [C027, C028] Orphan cleanup is a known-broken safety no-op motivated by WSL2 shutdown risk; the docs imply a module-level disabled flag, but source/tests show no such flag exists. Treat inline no-op methods as runtime truth and the flag claim as false. [C032, C033]

## Evidence

Source verification for the conductor/baton split comes from `src/marianne/daemon/process.py`, `src/marianne/daemon/baton/core.py`, and `src/marianne/daemon/baton/dispatch.py`: conductor startup uses advisory locking, `BatonCore` creates an unbounded inbox, and `dispatch_ready()` is a free function with global, per-model, rate-limit, and stagger gates. [C004, C005, C006, C007, C008, C009, C034]

For current musician/executor boundaries, begin with `src/marianne/core/sheet.py`, `src/marianne/daemon/baton/musician.py`, `src/marianne/daemon/baton/backend_pool.py`, `src/marianne/execution/`, `src/marianne/instruments/`, and current tests. The bundled source slices preserve the older pinned topology for historical comparison only [C002, C003, C020, C021, C023, C024, C025].

Source verification for plugin/tool architecture comes from `src/marianne/core/config/techniques.py`, `src/marianne/daemon/baton/techniques.py`, `src/marianne/daemon/technique_router.py`, and `src/marianne/execution/interface_gen.py`: techniques define `skill`, `mcp`, and `protocol`; active techniques are resolved per sheet phase; A2A/tool-like outputs are classified; compact MCP stubs are generated. [C010, C011, C012, C013, C014]

Source verification for state ownership and spec-only boundaries comes from checkpoint/state files plus baton adapter/events/core: job and sheet status enums exist, SQLite schema version 4 exists, A2A runtime state is in memory only, A2A completion/failure events are not executed, cron/config reload handlers are warning-only, grounding is config-only runtime-unwired, and orphan cleanup is a hardcoded no-op rather than a flag-controlled feature. [C026, C027, C028, C029, C030, C031, C032, C033, C041, C042, C044]

## Trap

Tempting sentence: "The conductor owns scheduling, cron, config reload, grounding, plugins, and A2A as implemented runtime features."

Correction: The conductor owns daemon lifetime, the baton owns event/state progression, `dispatch_ready()` owns scheduling gates, musicians own attempts through instrument backends, ECS techniques provide implemented skill/MCP/protocol access, and several named surfaces are only spec-only, observer-only, or runtime-unwired. [C004, C010, C012, C020, C026, C027, C028, C029, C030, C031, C034]

Concrete consequence: If you overclaim these boundaries, an operator may rely on cron jobs that never submit, config reloads that never rebuild pending sheets, grounding checks that never run, A2A completions that never propagate, or backend modules that do not exist after the Atlas migration. [C021, C023, C027, C028, C029, C030, C031]
