# Operating Marianne Jobs

## Problem

Operators are likely to treat a Marianne job as a normal shell command: run it, watch terminal output, retry on friction, and kill whatever looks stuck. That is unsafe because the real control boundary is the conductor, baton dispatch, validation process groups, checkpointed job and sheet status, and explicit pause/cancel state. Dispatch implements concurrency, rate-limit, and stagger gates, so waiting is often correct behavior rather than failure [C004, C005, C006, C007, C008]. Validation can run trusted-author shell commands and manages their process groups; an operator must not bypass that lifecycle by manually killing random children [C015, C016, C017, C018]. Job state has seven implemented values and sheet state has eleven implemented values, so monitoring should read state rather than infer truth from prose logs [C041, C042]. The guide also has to prevent overclaims: cron scheduling and config reload are spec_only, grounding is config_only_runtime_unwired, and orphan reaping is a known_broken_safety_noop without an operator flag [C029, C030, C031, C032, C033].

## Mechanism

Before submitting, run `mzt validate <score.yaml>` or inspect the score's validation contract, then use `mzt run <score.yaml>` only after the trust boundary is understood. Retryable validation types are bounded to `file_exists`, `file_modified`, `content_contains`, `content_regex`, `command_succeeds`, `path_in_scope`, `field_match`, `file_sha256`, and `csv_unique_key`; do not invent a retry policy outside those surfaces [C015]. Treat `command_succeeds` as implemented_security_sensitive because it is privileged bash for trusted score authors, and review command text before letting untrusted score content run it [C015]. If the score sets a relative workspace, it resolves against the score file parent and is not a confinement boundary, so only run trusted scores or pre-resolve paths in an operator-owned location [C038]. If prompt configuration is part of the change, reject simultaneous inline `template` and `template_file` before running [C039].

Submit through the conductor and let `dispatch_ready()` decide what can start. `dispatch_ready()` is the stateless scheduling boundary called after baton events [C004]. Code and tests show that `dispatch_ready()` enforces the global concurrency ceiling; one configuration reference denying enforcement is stale, so treat global enforcement as runtime truth and record the denial as stale docs [C005]. It also supports per-instrument or per-model concurrency, skips instruments currently marked rate-limited, and applies a monotonic-clock stagger delay [C006, C007, C008]. Therefore a sheet in `waiting`, `ready`, or `retry_scheduled` can be healthy if the relevant gate is active; rate limits are not failures unless the job exhausts its own policy and moves to a failed state [C007, C041, C042].

Monitor with `mzt status <job_id>`, `mzt watch <job_id>`, `mzt list`, `mzt logs`, `mzt errors <job_id>`, `mzt history <job_id>`, or `mzt diagnose <job_id>`, then interpret the result through the implemented enums. At job level, use only `pending`, `running`, `completed`, `failed`, `paused`, `paused_at_chain`, and `cancelled` as implemented status values [C041]. At sheet level, use `pending`, `ready`, `dispatched`, `in_progress`, `waiting`, `retry_scheduled`, `fermata`, `completed`, `failed`, `skipped`, and `cancelled` [C042]. Outcome summaries should use the six implemented outcome categories: success on first try, success after retry, success by completion, failed exhausted, failed fatal, and skipped by escalation [C043]. Cost reports can be uncertain: when pricing is missing, the runtime records `cost_uncertain` and zero cost, so do not present zero dollars as proof that no model was used [C036]. Captured output is capped at 51,200 bytes / 50 KiB and keeps trailing output; a stale 10KB test docstring is not runtime truth [C048].

Pause with `mzt pause <job_id>`, resume with `mzt resume <job_id>`, resolve a `fermata` with `mzt resolve <job_id>`, recover inconsistent state with `mzt recover <job_id>`, and cancel with `mzt cancel <job_id>`, then confirm the state transition through checkpoint/status records. A paused job should appear as `paused` or `paused_at_chain`; a cancelled job should appear as `cancelled` at job level and affected sheets should reach `cancelled` or a terminal state [C041, C042]. Let validation process cleanup run: command validation starts a new session, refuses a command that shares the daemon process group, and terminates the command process group with SIGTERM, a two-second grace period, then SIGKILL [C016, C017, C018]. Conductor start uses a PID file with `fcntl.flock` advisory locking, so duplicate-start detection is an implemented process guard [C034]. The event inbox is intentionally unbounded and is an implemented_security_risk for OOM or DoS if an operator or wrapper floods events; do not spam pause/resume/cancel or submit loops while waiting for dispatch gates [C009].

Never rely on surfaces that are documented but not executed. The docs say `CronTick` submits and reschedules jobs, but source/tests show the baton event loop only logs an unimplemented warning. Treat warning-only behavior as runtime truth and record scheduling prose as stale or contradicted [C029]. The docs say `ConfigReloaded` rebuilds pending sheets, but source/tests show it only logs an unimplemented warning. Treat warning-only behavior as runtime truth and record reload prose as stale or contradicted [C030]. The docs say grounding hooks validate outputs, but source/tests show grounding config validates structurally and no runtime path invokes hooks. Treat runtime-unwired grounding as truth and record active validation prose as stale or contradicted [C031]. The docs or claim say a module-level orphan-reaping disabled flag exists, but source/tests show no such flag and cleanup methods are hardcoded no-ops. Treat the no-op method bodies as runtime truth and record the flag claim as false [C032, C033].

## Evidence

The run path is source-backed by dispatch claims: `dispatch_ready()` is the scheduler [C004], global concurrency is implemented despite stale docs [C005], per-instrument/model concurrency is implemented [C006], rate-limit checks are implemented [C007], and stagger gating is implemented [C008]. These claims justify waiting during normal backpressure instead of treating every non-start as failure.

The control path is source-backed by status and process claims. Job status has exactly seven implemented values [C041], sheet status has eleven implemented scheduling values [C042], and outcome category has six implemented values [C043]. Validation commands are security-sensitive and process-managed: `command_succeeds` is trusted-author bash [C015], commands spawn in a new session [C016], the daemon-process-group guard exists but is implemented_untested [C017], and cleanup sends SIGTERM then SIGKILL to the validation process group [C018].

Operational caveats are not optional warnings. The event inbox is an unbounded queue and therefore an implemented_security_risk under event floods [C009]. Relative workspace path resolution is implemented_security_sensitive because score-relative paths can escape an assumed operator directory [C038]. Cost fallback sets `cost_uncertain` and zero cost when pricing is missing [C036]. Output capture is 51,200 bytes / 50 KiB, and a stale 10KB test docstring only matters as drift evidence [C048].

## Trap

Tempting sentence: "A waiting or retry-scheduled sheet means the run is broken."

Correction: "A sheet can wait because dispatch is enforcing global concurrency, per-instrument/model limits, rate limits, or stagger gates; rate limits are backpressure until the job reaches a failed terminal state." The consequence of the tempting sentence is unnecessary cancellation or duplicate submission while the scheduler is doing its job [C005, C006, C007, C008, C041, C042].

Tempting sentence: "If the job hangs, kill its child processes or restart the conductor."

Correction: "Use pause, resume, cancel, and status confirmation; validation commands already run in isolated process groups with guarded cleanup, and conductor PID locking is the process-level duplicate-start guard." The consequence is orphaned or corrupted control-plane state if manual process killing races the conductor [C016, C017, C018, C034].

Tempting sentence: "Cron, config reload, grounding, and orphan cleanup can recover the run."

Correction: "Those surfaces are spec_only, config_only_runtime_unwired, or known_broken_safety_noop; they will not schedule, rebuild, validate output integrity, or reap leaked processes at runtime." The consequence is false recovery and a job that appears managed while the intended action never executed [C029, C030, C031, C032, C033].

## Verify

1. Before run, use `mzt validate <score.yaml>`, confirm every score path and workspace path is trusted, and remember that relative workspaces resolve against the score file parent without confinement [C038]. Confirm prompt config does not set both inline `template` and `template_file` [C039].
2. Before submit, inspect validations. If `command_succeeds` appears, label it trusted-author privileged bash and verify the command is acceptable for this machine [C015].
3. During monitoring, read job status only from the seven implemented values and sheet status only from the eleven implemented values; do not infer terminal state from log tone [C041, C042].
4. Treat `waiting`, `ready`, and `retry_scheduled` as scheduler states to inspect, not immediate failures. Check global concurrency, per-instrument/model limits, rate-limit state, and stagger delay before retrying [C005, C006, C007, C008].
5. Pause, resume, resolve, recover, or cancel once, then verify the resulting checkpoint/status with `mzt status <job_id>` or equivalent state inspection. Do not flood the unbounded event inbox with repeated control events [C009, C041, C042].
6. Never promise cron scheduling, config hot reload, grounding enforcement, or orphan cleanup as recovery steps; source/tests win over stale docs for those contradicted surfaces [C029, C030, C031, C032, C033].
7. Scan the page for runtime verbs and attach claim IDs to each factual sentence or delete the sentence. Confirm every contradicted, stale, runtime-unwired, false, security-sensitive, or security-risk statement names its status and uses workspace claim IDs from `triangulation/triangulation.jsonl`.
